So funktioniert es im Code
modules/vanity_grinder.py
# EVM + Tron: Profanity-Algorithmus, inkrementelle Public-Key-Suche
# 1x teure Punkt-Multiplikation, dann nur Additionen (~9x schneller)
seed = randint(1, SECP256K1_N)
Q = seed * G                    # einmalig: secp256k1 Punkt-Multiplikation
for i in range(count):
    Q = Q + G                   # billige Punkt-Addition statt neuer Key
    h160 = keccak256(Q)[12:]  # letzte 20 Bytes
    if fmt == 'evm':   disp = '0x' + h160.hex()       # 16^n Alphabet
    if fmt == 'tron':  disp = b58check(0x41 + h160)  # T…, 58^n, sha256d-Checksum
    if match(disp, prefix, suffix):
        privkey = (seed + i) % n  # Key rekonstruiert (profanity2-Delta)
        assert verify_key(disp, privkey, fmt)  # Key→Adresse gegengeprüft
        return GrindResult(lookalike=disp, private_key=privkey)

# Solana: ed25519 — andere Kurve, Seed→Skalar ist nonlinear (SHA-512),
# der Q+=G-Trick ist mathematisch nicht anwendbar → frische Keys (~12k/s/Kern)
for _ in range(count):
    kp = ed25519.keypair()       # 32B seed + 32B pubkey
    disp = b58encode(kp.pubkey)  # KEINE Checksumme — Solana validiert nur Länge
    if match(disp, prefix, suffix):
        assert b58encode(ed25519(kp.seed).pubkey) == disp
        return GrindResult(lookalike=disp, private_key=kp)

# CREATE2: Contract-Lookalike — Salt statt Key, reine Keccak-Loop (~600k/s)
for i in range(count):
    salt = salt0 + i
    disp = keccak(0xff‖deployer‖salt‖keccak(init_code))[12:]
    if match(disp, prefix, suffix):
        return GrindResult(lookalike=disp, private_key=salt)
Echter Algorithmus aus profanity: statt jeden Key neu zu generieren wird der Public Key inkrementiert (Q += G) — der Private Key ergibt sich als (seed + offset) mod n. Genau dieses Delta-Design macht profanity2 outsourcing-sicher: eine GPU-Farm sieht nur den Public Key, nie den finalen Private Key. Erwartete Versuche: 16n (EVM) bzw. 58n (Tron/Solana base58). Gemessene Raten hier: ~250k/s EVM · ~300k/s Tron (gleiche secp256k1-Inkremente, nur base58check-Encoding) · ~100k/s Solana (ed25519, kein Increment möglich). GPU-Farmen: ~3,8 Mrd/s.

Experten-Fragen — Q&A Spickzettel
für die Präsentation
Warum funktioniert transferFrom ohne Allowance?
ERC-20 prüft require(allowance[from][sender] >= amount) — mit amount=0 ist 0 >= 0 immer wahr. Jeder kann Transfer-Events zwischen beliebigen Adressen erzeugen. USDT/USDC sind immutable deployed — bleibt für immer angreifbar (OpenZeppelin Issue #3931).
Warum ist der Angriff nicht patchbar?
Usability-Problem, kein Protokoll-Bug (USENIX): Wallets kürzen Adressen, Menschen kopieren aus der History. transferFrom(0) kann aus Kompatibilitätsgründen nicht entfernt werden. Einzige Defense: Wallet-seitig (History-Warnung, Adressbuch, volle Anzeige).
Wie schnell ist der Grinder wirklich?
Hier auf CPU: ~250k/s EVM, ~300k/s Tron, ~600k/s CREATE2 (keine EC-Mathematik), ~100k/s Solana (ed25519 — kein Increment möglich, Seed→Skalar ist nonlinear via SHA-512). GPU-Farmen (profanity2): ~3,8 Mrd/s auf einer RTX 4090.
Warum kann Solana den Increment-Trick nicht?
ed25519 leitet den Skalar per SHA-512-Hash aus dem Seed ab — nonlinear, kein Q+=G. Jeder Kandidat braucht einen kompletten Hash+Curve25519-Scalar-Mult. EVM/Tron teilen secp256k1 → dort gilt profanitys Q+=G-Inkrement.
Kontrolliert ein Key EVM + Tron gleichzeitig?
Ja — Tron nutzt secp256k1, nur anderes Encoding: base58check(0x41 ‖ keccak(pubkey)[12:]). Derselbe Private Key kontrolliert die 0x-Adresse und die T…-Adresse. Im Demo verifiziert (Targeting-Step erzeugt beide aus einem Key).
Warum ist Solana das gefährlichste Ziel?
Keine Checksumme in der Adresse — ein einzelnes falsches Zeichen sendet still ins Nichts. EVM/Tron haben EIP-55/sha256d-Checksum, die Vertipper abfängt. Phantom hat bis heute nur partielle Detection.
Was hat sich 2026 geändert?
MetaMask + Trust Wallet shipped History-basierte Poisoning-Detection (Blockaid / Intel Security API): eingefügte Adresse wird gegen frühere Gegenparteien verglichen — gleiche Enden, andere Mitte → blockierende Warnung. Folge: Massen-Angriffe wandern zu Tron/Solana/alten Wallets ab.
Was ist CREATE2-Grinding?
Contract-Lookalikes: keccak(0xff‖deployer‖salt‖keccak(init_code))[12:] — der Salt wird gebruteforced statt des Keys, reine Keccak-Loop ohne EC-Mathematik → schnellster Pfad. Praxis-Einsatz: Vanity-Contracts (Uniswap V4 Hooks), metamorphic Contracts, Fake-Token-Adressen.
Woher kommen die Erfolgszahlen?
USENIX Security '25: 270M Angriffe, 6.633 Opfer → p ≈ 2,47e-5, erster Erfolg ~40.700 Einträge. Bitquery 12-Monats-Messung: $19,2–25,5M Gas vs. $22–144M Erlös. CCS'24 Poison-Hunter: 2.900 Batching-Contracts, 2.300 Fake-Tokens, 4 Cluster kontrollieren 98% der Phishing-Adressen.
Warum BSC für Masse, Ethereum für Ertrag?
BSC: ~1 gwei Gas → $0.009/Eintrag → 252,7M Angriffe (94%) aber nur $4,5M. Ethereum: nur 6% der Angriffe aber $79,3M = 95% des Schadens (Ø-Opfer-Balance $338.900). Dieselbe 0x-Lookalike-Adresse gilt auf allen EVM-Chains — Angreifer fahren Cross-Chain mit einer Adresse.

Doku — wie das System funktioniert

Address Poisoning in einem Satz: Der Angreifer erzeugt eine Adresse, die vorne und hinten gleich aussieht wie eine Adresse aus deiner Wallet-History, und schleust sie per Fake-Transfer in deine Liste ein — du kopierst beim nächsten Senden die falsche Adresse. Warum das nie verschwindet: Es ist kein Bug, sondern Bequemlichkeit — Wallets kürzen Adressen (0x1234…abcd), Menschen kopieren aus der History statt "Empfangen" zu nutzen. Stand September 2026: MetaMask + Trust Wallet blockieren das mittlerweile aktiv (History-Vergleich), deshalb sind die Kampagnen auf Tron, Solana und ältere Wallets gewichen.
Phase 1 — Aufklärung
Recon
Watcher — liest Transfer-Events der Chain live mit. Warum: Ohne Beobachtung weiß der Angreifer nicht, wann das Opfer zuletzt gesendet hat. modules/indexer.py · detection_watcher.py

Targets — Queue der potenziellen Opfer. Warum: Massen-Angriffe brauchen Millionen Adressen; gezielte Angriffe wenige wertvolle.

ML-Scoring — RandomForest rankt Opfer nach 16 On-Chain-Features (Guthaben, Aktivität, Counterparties). Warum ML statt fixer Regeln: Das Opfer-Muster ist bekannt, aber die Schwellen wandern mit der Defense-Lage — neue Labels rein, neu trainieren, fertig. Live-Loop: bestätigte Poison-Treffer (Opfer sendet echten Wert an Lookalike) werden automatisch zu neuen Labels. modules/ml_scorer.py · behavioral_analyzer.py · /api/ml/hits

Autonomous Agent — RL-Agent der Opfer selbst priorisiert und Exchanges ausschließt (die würden einfrieren). modules/autonomous_agent.py
Phase 2 — Angriff
Kern
Grinder — berechnet Lookalike-Adressen per Brute-Force. Wie: secp256k1-Inkrement Q += G (profanity-Algorithmus) statt frischer Keys — ~9× schneller. EVM keccak→0x, Tron 0x41+base58check (gleicher Key!), Solana ed25519 (kein Increment möglich), CREATE2 Salt-Grinding für Contracts (reine Keccak-Loop, schnellster Pfad). Warum: Das Match auf die sichtbaren Enden ist die Täuschung — 16n bzw. 58n Versuche. modules/vanity_grinder.py

Targeting-Prozess — End-to-End: Opfer analysieren → Lookalike erzeugen → Poison-TX pro Chain bauen. Der Trick: transferFrom(opfer, lookalike, 0) — Allowance-Check 0 >= 0 ist immer wahr, jeder darf Fake-History schreiben. Tron: triggerSmartContract auf echten USDT-TRC20, Solana: SPL transferChecked. modules/targeting_process.py · transaction_builder.py

Sweeper — räumt eingehende Gelder sofort ab, bevor das Opfer reagiert. Warum: Zeitfenster ist klein — die Praxis-Cluster sweepen innerhalb von Sekunden. modules/sweeper.py
Phase 3 — Verteidigung
Defense
Detection — erkennt Poison-Muster: gleiche Enden + andere Mitte, 0-Value-Transfers, zeitliche Nähe zur echten TX. modules/detection_engine.py · risk_engine.py

Policy Attestation — PACE-Pattern: jede TX wird gegen Policies geprüft (Limits, Exchange-Ausschluss, Risiko-Schwelle) und die Entscheidung signiert — nachvollziehbar, nicht manipulierbar. modules/policy_attestation.py

Wallet-Defense-Matrix (Grinder-Seite): MetaMask/TrustWallet aktiv seit 2026, Phantom teilweise, TronLink keine. Kernpunkt: Defense existiert nur wallet-seitig — das Protokoll kann transferFrom(0) aus Kompatibilität nicht entfernen.
Infrastruktur
Skalierung
GPU-Scaling — Auto-Scale auf GPU-Farmen (RTX 4090: ~3,8 Mrd Keys/s vs. ~250k/s hier auf CPU). Warum: Praxis-Patterns (4+4 EIP-55) sind nur mit GPU rentabel — genau deshalb zeigt der Advisor CPU vs. GPU. modules/gpu_scaler.py

Chain-Integration / RPC — EIP-1559-Gas, Testnet-Anbindung, echte TX-Signierung und Broadcast via send_raw_transaction sobald RPC+Key konfiguriert sind. Mit WebSocket-URL läuft zusätzlich der Live-Watcher (echtes eth_subscribe). modules/chain_integration.py · rpc_connector.py

Multi-Agent — verteilte Knoten mit Leader-Election; spiegelt die Cluster-Infrastruktur (USENIX: 4 Cluster kontrollieren 98% der Phishing-Adressen). modules/multi_agent_coordinator.py
Technik-Stand September 2026
Recherche
Verteidigung: MetaMask (Blockaid, History-Vergleich, 65,4M Poison-TXs geflaggd Jan 2025–Feb 2026) + Trust Wallet (Intel Security API, 32 EVM-Chains) blockieren den klassischen 4+4-Angriff seit 2026 → die Szene ist gewandert: Tron (TronLink ohne Defense, gratis Bandwidth), Solana (keine Checksumme, Phantom nur partiell), ältere Wallet-Versionen, Exchange-Flows.

Angriffs-Skalen (gemessen): USENIX '25: 270M Angriffe, 6.633 Opfer, erster Erfolg statistisch nach ~40.700 Einträgen. BSC = 94% der Masse ($0.009/Eintrag), Ethereum = 95% des Schadens ($79,3M). Post-Fusaka (billigeres Gas): USDT-Poisons +612%. ROI der Cluster: >220%.

Offen / nicht abgedeckt in dieser Demo: Counterparty-Auto-Pick (häufigste Gegenpartei direkt als Grind-Ziel), Permit/Approval-Phishing (andere Angriffsklasse), Clipboard-Hijacking (Malware, kein On-Chain-Vektor), ENS-Name-Spoofing.

RPC-Betrieb: Node auf der RPC-Seite anschließen — HTTP allein aktiviert Status, Gas und echten chain/send-Broadcast; mit WebSocket-URL läuft zusätzlich ein echter eth_subscribe-Feed (Transfer-Feed, Zero-Value-Alerts, Logs werden live befüllt).
